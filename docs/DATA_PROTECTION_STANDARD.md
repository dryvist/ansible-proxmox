# Data Protection Standard

The governing standard for how every piece of state in the homelab is
protected — databases, config, object storage, ZFS pools, and anything added
later. Individual mechanisms (`DATABASE_DR_STANDARD.md`, `DR_RUNBOOK.md`, each
role's README) implement this standard; they do not set their own targets.

## Why three numbers, not one

RPO alone is not enough to describe protection. A real-time streaming
replica can have an RPO of seconds and still faithfully replicate a
`DROP TABLE` five minutes after it happens — the replica is fresh and the
data is gone. **Recovery window is a peer of RPO, not a footnote**: it is how
long you can reach back before the mistake, not just how current the copy is.

Every protection class is therefore three numbers:

| Class | RPO | RTO | Recovery window |
| --- | --- | --- | --- |
| **P0 — continuous** | ≤ 60 s | ≤ 30 min | ≥ 30 d, ≥ 7 d immutable |
| **P1 — near-realtime** | ≤ 15 min | ≤ 4 h | ≥ 30 d |
| **P2 — exemption** | ≤ 24 h | ≤ 24 h | ≥ 14 d |
| **P3 — declared none** | ∞ | rebuild | none |

- **RPO** — how much recent data can be lost.
- **RTO** — how long until the data is available to restore into a rebuilt guest.
- **Recovery window** — how far back in time you can still reach, so an
  error discovered late is still recoverable, not just a fast crash-loss.

## Assignment rule

Every data store is assigned a class by answering three questions, in order.
Stop at the first one that applies.

1. **Is it reproducible byte-for-byte from IaC, or re-downloadable from a
   public source?** → **P3.** There is nothing to protect; the source of
   truth lives elsewhere and regenerating it is the recovery path.
2. **Does anything outside the repo — a human, an external API, a sensor —
   write to it such that the last hour cannot be recreated?** → **P0.** This
   is state nothing else remembers.
3. **Otherwise** → **P1.**

**P2 does not exist at the end of this tree — it is unreachable by
construction.** The only way into P2 is a written exemption with a named
owner and a stated reason, recorded in the class-assignment table below.
That asymmetry is deliberate: it is how "cold standbys are not an option"
gets encoded honestly. The default for anything new is P0 or P1; anything
slower than that is a decision someone signed, not a default anyone drifted
into.

### Be honest about RTO

Nothing in this lab has automated failover for stateful services — see
[`DR_RUNBOOK.md`](DR_RUNBOOK.md). "RTO ≤ 30 min" means the data is available
to restore into a rebuilt guest within 30 minutes, not that the service
self-heals. Do not write an RTO here that a drill cannot demonstrate.

## Derived vs source of truth

The organizing idea behind every class assignment: is this store a **source
of truth** (something writes to it that cannot be recreated), or is it
**derived** (an index, cache, or rebuild target that some other source of
truth already covers)? That one distinction collapses roughly two dozen
special-cased stores down to three classes plus one exemption tier — nothing
here is protected or exempted by name, only by which side of that line it
falls on.

| Store | Class | Owner | Reason |
| --- | --- | --- | --- |

| SQLite: authelia, the *arr stack, plex, ntfy, healthchecks, hermes | P0 | infra | Same — each file is written to directly by its app. |

| `bulk/appdata` | P1 | infra | Changes on a deploy/config cadence, not continuously. |

| Prometheus TSDB | P3 | infra | Already remote-writes to Splunk; the local TSDB is a scrape cache, not a store of record. |

| LLM weights | P3 | infra | Re-downloadable from the model's public source. |
| Cribl PQ | P3 | infra | A transient on-disk buffer for in-flight events — drained or replayed from source, never restored from backup. |

## The telemetry contract

Every protection mechanism appends one line per run to
`/var/log/data-protection/<mechanism>.status`. Mandatory fields:

```text
ts host mechanism job class outcome age_seconds
```

Three rules are binding, each written because something already broke this way:

- **`age_seconds=-1` means NEVER.** Never emit `0` for "unknown" or leave the
  field blank — a parser reading `-` as `0` sees "just synced," which hides
  the exact failure worth catching. The `pvesr` `postgres-apps` job had never
  run once while its dashboard read green; nothing distinguished "just
  synced" from "has never synced."
- **A host with nothing to do emits `job_count=0`.** Silence from a healthy
  host with no jobs assigned must stay distinguishable from silence from a
  dead one.
- **`outcome` is a closed vocabulary: `ok|fail|skip`.** A `skip` is **not** a
  success and must carry a non-empty `reason=`. The workstation-capture
  backup exited `0` for months, logging "no target configured — skipping,"
  and read as healthy the entire time.

**Alerting happens in Splunk, never at the source** — this is the same rule
as [`observability-and-alerting.mdx`](https://docs.jacobpevans.com/d/conventions/observability-and-alerting/):
a mechanism emits facts, it never decides severity or notifies. Absence is
caught the same way as everywhere else — a left-join in Splunk against
`data_protection_expected.csv`, generated from the same Ansible vars that
create the jobs. A job that never reports at all is a **missing row**, not
silence to be individually alerted on.

### Scheduling vs collection

The observability convention says filesystem reads and small scripts run
under Cribl Edge, "not cron, not a systemd timer." Read literally that
collides with this standard, which needs systemd timers for real work. The
resolution: **the observability convention governs collection, not workload
scheduling.**

- **Doing work** — replicating, dumping, uploading, running a restore
  drill — is a **systemd timer**. It needs ordering, timeouts, `OnFailure=`,
  and randomized delay; Cribl Edge has none of those.
- **Producing a signal about work already done** is a `.status` line,
  written by that timer's unit.
- **Reading state to produce a fact with no work attached** — checking a
  file's age, counting rows, tailing a log — is Cribl Edge.

## Adding a new data store

1. Answer the three assignment-rule questions above; record the class,
   owner, and (for P2/P3) the reason in the table.
2. Wire the mechanism that gets it to that class's numbers — a
   `*_standby`-style pull job (see `DATABASE_DR_STANDARD.md`), a `sanoid`
   template, or an upload step. Reuse an existing mechanism before writing a
   new one.
3. Have it append to `/var/log/data-protection/<mechanism>.status` on every
   run, following the telemetry contract above.
4. Add the job to the Ansible vars that generate `data_protection_expected.csv`,
   so its absence is detectable.
5. Run the restore drill and record that it passed.

Two hard gates:

- **No new protection job may target or source the retired node.** Its
  `bulk` pool is a DEGRADED raidz1 with a REMOVED member.
  Anything landing there today is building on a pool already down a drive.
- **A store is not "protected" until its restore drill has passed once** and
  it appears in `data_protection_expected.csv`. A mechanism that has never
  been proven to restore is a guess, not a protection.
